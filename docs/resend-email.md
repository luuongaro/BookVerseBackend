# Email delivery with Resend

Render's `render` profile now selects the Resend HTTPS API by default. All three messages (welcome, password recovery and password-change confirmation) go through the same delivery interface. The local default remains SMTP; set `MAIL_PROVIDER=resend` locally to use the HTTPS provider there too.

## Set up Resend before deploying

1. Create or open the team's Resend account.
2. Add and verify `bookverse.com.ar`, or a dedicated sending subdomain owned by the team. Copy the DNS records generated by Resend to the domain's active DNS provider. Use the exact records from that account. Verification requires access to the DNS zone.
3. Create a **Sending Access** API key scoped to the sending domain.
4. Set these variables directly in Render's Environment screen:

| Variable | Value |
| --- | --- |
| `MAIL_PROVIDER` | `resend` (also the Render profile default) |
| `RESEND_API_KEY` | The private Resend Sending Access key |
| `MAIL_FROM` | A sender on the verified domain, for example `BookVerse <notificaciones@bookverse.com.ar>` |

A Gmail address cannot serve as a sender for a domain the team verifies in Resend. The sender must match the verified domain. A `resend.dev` test sender is restricted and is not the production sender for BookVerse users.

`MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME` and `MAIL_PASSWORD` are not required by the Resend path. Existing SMTP settings may remain present; `MAIL_PROVIDER` selects the transport. SMTP settings are only used when `MAIL_PROVIDER=smtp`.

When `MAIL_PROVIDER=resend`, a missing API key causes a clear startup failure instead of silently accepting mail that cannot be delivered. Configure the key before deploying this code. If this deployment also introduces password recovery, apply `docs/sql/password-recovery.sql` in Supabase before deploying the backend.

## Implementation and operational checks

- The delivery client posts JSON to the fixed endpoint `https://api.resend.com/emails`, with a backend-only bearer credential. No additional SDK or frontend secret is needed.
- Each request has a unique idempotency key. Connection and response waits are bounded to 5 and 10 seconds respectively.
- Only successful HTTP responses are accepted. Provider errors expose only the HTTP status in application logs; response bodies, API keys, recipients and recovery links are not logged. Transport errors use status `0`.
- Delivery failures do not fall back to SMTP. Inspect the corresponding Resend API log to diagnose a rejected key, sender/domain validation issue or quota limit. A successful API response means the provider accepted the message; confirm delivery separately in Resend and the recipient's inbox.
- Real mail delivery remains to be verified after the account, domain, variables and deployment are ready. No real credentials or outbound email were used in automated checks.

## Tests

```sh
./mvnw -Ppassword-recovery-tests package
```

37 focused backend tests pass and the executable jar is built. Checks include the exact HTTPS URL, bearer header, recipient array, recovery link, response handling for redirects and HTTP 401/403/422/429/500/503, connection failures, missing keys, provider selection using the checked-in YAML, SMTP compatibility, and the password recovery/JWT/transaction tests. HTTP calls are intercepted by MockRestServiceServer; SMTP and mail recipients are mocked. The default complete legacy test compilation still has the pre-existing reviews/subscriptions errors.
